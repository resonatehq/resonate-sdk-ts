# Decentralized Resonate on S3

`S3Network` is a `Network` with no server behind it.

Every other network in this SDK is a transport: it carries a request to a
Resonate Server and carries the response back. This one is not. The SDK *is*
the server — it carries the protocol's transition relation and runs it locally
against two S3 buckets it reads and writes directly.

```ts
import { Resonate } from "@resonatehq/sdk";
import { S3Network, awsBucket } from "@resonatehq/sdk/s3";

const resonate = Resonate.remote({
  network: new S3Network({
    // One document per workflow. Express is the right bucket class here.
    workflows: await awsBucket({ bucket: "acme-wf--use1-az4--x-s3", region: "us-east-1" }),
    // One document per wakeup. MUST be a general purpose bucket.
    timeouts: await awsBucket({ bucket: "acme-timeouts", region: "us-east-1" }),
    shard: { index: 3, count: 5 }, // this process is shard 3 of 5
  }),
});
```

The design is the meeting point of three prior arts:

* the **Turso network** in this SDK (`src/network/turso` on its branch) — the
  origin partition, the protocol port, the sharded fleet;
* **resonate-on-s3** (Rust) — the document model, the ETag CAS loop, the
  coverage law and the delta rule;
* **celld** (`celld.dev`) — the time-bucket key scheme for wakeup entries in
  object storage.

## One workflow, one document

Every promise id is prefixed by its **origin** — the root workflow's id,
everything before the first `.`. `S3Network` gives each origin one JSON
document under one key, `wf/<origin>`, in the workflow bucket.

That is not an arbitrary sharding key. The protocol already guarantees a
callback never crosses an origin (`promise.register_callback` refuses one), so
every request touches exactly one workflow's state. A workflow is a unit of
consistency, and here it becomes the unit of storage *and of atomicity*: the
document holds everything about one workflow — its promises, the callbacks and
listeners registered against them, its tasks, buffered resumes, and the armed
timeouts — and every transition is one conditional PUT of that document.

**No log, no claim, no fencing.** The whole concurrency model is one loop:
GET the document (and its ETag), decide in memory, PUT it back conditionally —
`If-None-Match: *` to create, `If-Match: <etag>` to replace — and on conflict
re-get and re-decide (bounded at 64 attempts). A zombie writer is not fenced;
its PUT simply fails. Two rules keep the loop honest:

* **The write law.** A step that changed nothing writes nothing. Reads,
  idempotent replays, and too-early ticks are pure GETs.
* **Recognition.** A PUT whose fate is unknown (network error after the bytes
  may have reached the store) is resolved by re-reading and recognizing our
  own write by byte equality — identical bytes are identical state. This is
  also why the AWS driver disables SDK retries on the CAS path: a
  transparently retried conditional PUT whose first attempt landed answers
  412 to the retry, converting "may have committed" into a false rejection.

**S3 Express is the right home for this bucket** — single-digit-millisecond
GET/PUT, high TPS, and the conditional-write API is identical to a general
purpose bucket's, so Express is a bucket choice, not a code path. The
workflow bucket is never listed on the hot path, so Express's unordered
listing costs nothing.

## One timeout, one document — in time buckets

The timeout bucket is the one thing the whole fleet shares: it is how a
process finds work in a workflow it has never seen. It holds one small
document per armed wakeup, keyed by **time bucket**:

```
t/<YYYY-MM-DDTHH:MM>/o/<origin>     an origin's earliest armed deadline
t/<YYYY-MM-DDTHH:MM>/s/<schedule>   a schedule's next run
sched/<schedule>                    the schedule document itself
```

The bucket component is minute-precision UTC (celld's scheme), shaped so that
**lexicographic key order is chronological order**. The sweeper lists the
`t/` prefix in key order, oldest first, and stops at the first key past the
present — the cost of a sweep is O(due), not O(armed). Entries are deleted as
they are consumed, so the listing stays O(armed wakeups) overall.

**This is why the timeout bucket must be a general purpose bucket, not S3
Express**: `ListObjectsV2` returns keys in ascending UTF-8 order on a general
purpose bucket, while a directory bucket's listing order is unspecified.
Ordering is the feature. (The workflow bucket has the opposite preference —
latency over listing — which is why the two are separate buckets.)

Entries are **hints, never the authority**. An entry says "look at this
origin around this minute"; the origin document remains the truth about what
is due, every timeout transition re-checks its own armed time before acting
(the spec's NOT BEFORE rule), and a too-early fire changes nothing and costs
nothing durable. Spurious entries, duplicates, and stale entries are all
safe; a consumer that finds nothing due deletes the entry and moves on. Only
*loss* is forbidden — a lost entry is a lost wakeup, recoverable only by
scanning every document — and three rules guard against it:

* **The coverage law.** For every armed deadline in any landed document, an
  entry at (a bucket ≤ that deadline, that origin) exists. Enforced by phase
  order, not discipline: when a step moves an origin's earliest armed
  deadline, the entry is written durably **before** the document. If the
  entry cannot be made durable, the step fails CLOSED — no put without a
  durable wakeup.

* **The delta rule.** A step arms an entry iff it changed the origin's
  *minimum* armed deadline. A fire that re-arms changes the minimum and so
  re-arms its own cover before its own put; an unchanged minimum keeps the
  prior, not-yet-completed entry as cover. One entry per origin per deadline
  movement — not one per timer — keeps write traffic proportional to
  progress.

* **Fire then complete.** The sweeper deletes an entry only after the tick it
  fired has landed, and only when the document's new minimum lives in a
  different time bucket (otherwise the entry is still the cover). A crash
  between fire and complete leaves the entry; the next sweep re-fires; ticks
  are idempotent by the write law.

## Messages are not stored

When a transition emits an `execute` or `unblock`, the message is handed to
the local Resonate client as soon as the document lands. No outbox, no queue,
no routing table — and a conflicted attempt's messages are discarded with its
document, so a message is only ever delivered for a state change that
actually happened.

Reaching a **different** process therefore goes through time, not through a
queue. A dispatched task carries a durable retry timer; if nobody claims it,
the timer comes due, and whichever process sweeps the timeout bucket re-emits
the execute and delivers it to its own client. Recovery is the timer — which
is exactly why the timeout bucket is the one thing shared.

The consequences are the Turso network's, unchanged:

* **`resonate:target` is advisory.** A message goes to whoever did the work,
  which is what you want in a homogeneous fleet (every process registers the
  same functions) and wrong in a heterogeneous one.
* **Unsharded, a result computed on one node does not reach the node waiting
  for it** — the finisher delivers the `unblock` to itself, and the waiter
  falls back on its own slow path. Sharding closes this: one owner per
  workflow means the node that finishes a workflow is the node that was
  waiting on it.

## One process, one shard — and shards are dynamic

```ts
new S3Network({ workflows, timeouts, shard: { index: 3, count: 5 } })
```

"This process is shard 3 of 5." A sharded node sweeps only the wakeups of
origins it owns — `hashOrigin(origin) % count === index` — filtered at the
sweep, before entries fill its batch. The caller routes requests to the
owning node with the same function (`ownerOf(originOf(id), count)`, exported
for exactly this), so routing and sweeping cannot disagree. The hash is
32-bit FNV-1a, pinned by test vector and shared with the Turso network and
the Python SDK's `hash_origin`.

One owner per workflow buys three things: a workflow stops migrating between
nodes mid-flight; one owner means one writer, so the document CAS almost
never conflicts (contention retries the loop, correctly, but every conflict
is a wasted round trip); and the unblock problem above disappears.

**Shards are dynamic in the sense that matters.** Nothing in either bucket
encodes the member count — the hash is a property of the origin alone, and
every entry carries its origin in the key. Resizing the fleet from 5 to 7 is
a configuration change (each node restarts with the new `count`), not a data
migration. During a resize, an origin's old and new owner may briefly both
sweep it; the CAS makes that safe (one of the two wastes a conflict), which
is the difference between sharding here and sharding on the Turso sync
driver, where a double-writer is unsound and sharding is the correctness
boundary. Here sharding is a latency-and-liveness optimization; correctness
comes from the conditional PUT.

Unsharded (the default), every node owns everything: correct, and the right
mode for a single process or for tests.

## Schedules

A schedule belongs to no origin — its promise id is a template, so the
promises it fires may land anywhere. Each schedule is one document
(`sched/<id>`) in the timeout bucket, advanced by ETag CAS like any workflow,
with a wakeup entry (`t/<bucket>/s/<id>`) armed for its next run **before**
the schedule document lands — the coverage law again. Occurrence promise ids
are per-occurrence (`{{.timestamp}}` / `{{.id}}` expansion), so a crashed or
raced firing re-fires idempotently: the promise is already there, and the
losing advance simply conflicts.

## What the wire pays

Per request (steady state, sharded owner):

| Operation | Workflow bucket | Timeout bucket |
|---|---|---|
| Read (`promise.get`, searches) | 1 GET | — |
| Write, min deadline unchanged | 1 GET + 1 PUT | — |
| Write, min deadline moved | 1 GET + 1 PUT | 1 PUT |
| Sweep tick, nothing due | — | 1 LIST |
| Sweep tick, one origin due | 1 GET + 1 PUT | 1 LIST + 1 DELETE (+1 PUT re-arm) |

The idle cost of a node is one LIST per tick (default 250ms) against the
timeout bucket. There is no per-workflow polling: workflows the sweep does
not name are never touched.

## What is not supported

Identical to the Turso network, for the same partition reasons:

* **Tenant-wide `promise.search` / `task.search`** answer `501`; narrow with
  a `resonate:origin` tag or header and they are served from that one
  document.
* **Tenant-wide `debug.snap`** answers `501`; set the `resonate:origin`
  header to snapshot one workflow.
* **`http://` listener addresses** are emitted to the local client but never
  called — there is no server to make the call.
* **Detached (re-rooted) lineages** (`ctx.detached`): the origin partition
  cannot represent a root whose id contains `.`; `promise.create` refuses the
  tag with a 400 naming this limitation.

## Buckets and drivers

`S3Bucket` is the whole storage contract: `get`, conditional `put`
(create / replace-if-ETag-matches), `delete`, and ordered `list`. Two
implementations ship:

| Driver | Use |
|---|---|
| `awsBucket` | `@aws-sdk/client-s3` (optional peer dependency, imported dynamically); retries disabled on the CAS path; 412/409 → conflict, ambiguous transport errors surfaced as `unknown` for the recognition pass |
| `MemoryBucket` | the lock-atomic reference implementation — conditional semantics and sorted listing in memory; what the tests run against, and the contract `awsBucket` must match |

Anything S3-compatible with conditional writes (MinIO, R2, Tigris, ...)
works through `awsBucket`'s `endpoint`/`forcePathStyle`, or implement
`S3Bucket` directly.

Operational notes for real S3:

* **Conditional writes need no bucket configuration**, but the IAM policy
  needs `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, and
  `s3:ListBucket` on the two buckets.
* **Express directory buckets** return non-MD5 ETags; the code treats ETags
  as opaque, as it must.
* **Versioned general purpose buckets** work but accumulate noncurrent
  versions of every wakeup entry; a lifecycle rule that expires noncurrent
  versions keeps the timeout bucket tidy.
* The timeout bucket's keyspace is time-ordered by design, which concentrates
  writes on "now"; S3 partitions by key prefix, so an extremely hot fleet
  should watch for 503 backoff on the `t/` prefix. The per-origin delta rule
  keeps this traffic proportional to deadline movement, not to request rate.

## Tests

```shell
npx jest tests/s3.test.ts
```

The suite drives the network at the protocol level (promises, tasks,
timeouts, schedules, sharding, the declared-origin header), asserts the
storage shape directly (one document per workflow; wakeup entries keyed by
time bucket, armed before the workflow lands, completed after the fire; a
stale entry validated and swept; two processes racing one acquire producing
exactly one winner), and runs both engines end to end — including a workflow
abandoned mid-flight by one process and finished by another that discovered
it through the timeout bucket. Everything runs against `MemoryBucket`; no
credentials, no network.
